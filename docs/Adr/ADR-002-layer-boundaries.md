# ADR-002: Границы слоёв и правила зависимостей

Дата:    2026-08-17
Статус:  Принято

## Контекст

Проект делает один программист без ревьюера. Нужен механизм, который
проверяет архитектурные правила автоматически — компилятором, а не
дисциплиной. Отдельная и более острая причина: явное решение не
использовать `GameManager`-подобные объекты с размытой зоной
ответственности (см. также ADR-004 — паттерны и Composition Root,
дозавести при необходимости).

## Рассмотренные варианты

1. **Один общий Assembly-CSharp**, границы — по соглашению и папкам.
   Отклонён: соглашение ничего не проверяет, `UnityEngine` может
   протечь в правила игры на второй неделе и никто этого не заметит.
2. **Границы через `.asmdef`** с флагом `noEngineReferences` у домена.
   Нарушение становится ошибкой компиляции.

## Решение

Семь сборок, зависимости — только внутрь:

| Сборка | Назначение | Ссылается на |
|---|---|---|
| `Echo.Domain` | Правила игры: типизированные идентификаторы (`EntityId`, `AbilityId`, `ItemId`), контексты состояния (`RunContext`, `SessionContext`, `RegionContext`), шина событий (`IEventBus`, `EventBus`, `Subscription`). Флаг **No Engine References** включён. | ни на что |
| `Echo.Application` | Сценарии использования домена, порты (интерфейсы для инфраструктуры) | `Echo.Domain` |
| `Echo.Infrastructure` | Реализации портов: файлы, Addressables, Input System и т.п. по мере подключения | `Echo.Application`, `Echo.Domain` |
| `Echo.Presentation` | MonoBehaviour-вью, анимации, UI | `Echo.Application`, `Echo.Domain` |
| `Echo.Composition` | Три `LifetimeScope` (`AppScope`, `GameplayScope`, `RegionScope`), точки входа, отладочные пробы | всё |
| `Echo.Editor` | Инструменты редактора | всё, только в редакторе |
| `Echo.Tests.Domain` / `Echo.Tests.Play` | Тесты EditMode / PlayMode | `Echo.Domain` / всё |

Флаг **No Engine References** у `Echo.Domain` — не рекомендация, а
жёсткое ограничение: `using UnityEngine;` в этой сборке не
скомпилируется. Это единственная проверка архитектуры, которая
работает без силы воли и без ревьюера.

### Три области времени жизни (Composition Root)

`Echo.Composition` содержит три вложенные области VContainer:

```
AppScope        — вся сессия: настройки, профиль игрока
  └─ GameplayScope   — одно прохождение: RunContext, отпечаток, таланты
       └─ RegionScope    — один регион: спавн, погода, пулы
```

Дочерняя область видит регистрации родительской, обратное не работает.
Это прямая замена `GameManager`: вместо одной точки с глобальным
доступом и размытой ответственностью — три точки с чётко ограниченным
временем жизни. Уничтожение `GameplayScope` гарантированно убирает
всё состояние прохождения, не требуя вручную вспоминать, какие поля
обнулить.

Корректность иерархии на день написания ADR подтверждена
автоматическим PlayMode-тестом `ScopeLifetimeTest`
(`Echo.Tests.Play`): дочерняя область видит регистрации родителя,
родитель не видит регистраций потомка, уничтожение `GameplayScope`
диспозит `RunContext` (через `IDisposable`) и не трогает
`SessionContext`, `IEventBus` — общий на все уровни вложенности.
Пробы (`AppScopeProbe`, `GameplayScopeProbe`, `RegionScopeProbe`)
остаются как инструмент ручной проверки в редакторе, тест их не
заменяет полностью — они проверяют разные вещи: тест подтверждает
логику библиотеки на упрощённой сборке scope'ов, пробы дают увидеть
происходящее глазами при работе с реальными сценами.

**Известный пробел, требующий отдельной задачи.** `ScopeLifetimeTest`
собирает иерархию областей вручную через `LifetimeScope.Create(...)`,
а не поднимает настоящие `AppScope` / `GameplayScope` / `RegionScope`.
Это подтверждает корректное понимание поведения VContainer, но не
ловит регрессию вида «кто-то забыл зарегистрировать зависимость в
реальном `Configure()` продакшен-класса» — такая ошибка пройдёт мимо
теста молча. Нужен второй, интеграционный тест поверх настоящих
классов сцен; заводить отдельным пунктом, не заменяя существующий
тест, а дополняя его.

### Шина событий

`IEventBus` / `EventBus` / `Subscription` живут в `Echo.Domain` —
это обычные C#-классы без ссылок на движок. Подписка возвращает
`IDisposable`, отписка обязательна. Шина используется только для
свершившихся фактов (см. основной документ архитектуры, раздел 4.5) —
не для запросов и не для команд.

## Последствия

+ Правила игры тестируются без Play Mode — секунды, а не десятки
  секунд на перезагрузку домена.
+ Нарушение границы — ошибка компиляции, а не замечание на ревью,
  которого при одном программисте всё равно не будет.
+ Перерождение (когда до него дойдёт очередь) станет дешёвым:
  пересоздание `GameplayScope` вместо ручного обнуления состояния.
- Каждый новый тип, который должен использоваться и в домене, и в
  представлении, требует думать, в какой сборке он должен жить —
  небольшой, но постоянный когнитивный налог.
- Порог входа для человека, впервые открывшего проект: непонятно
  сразу, откуда берутся зависимости у объекта на сцене. Компенсируется
  этим ADR и README.

## Подтверждено

*Структура `Application/{Run, Session, World}` подтверждена кодом
(`using Echo.Application.Run;`, `using Echo.Application.Session;` в
`ScopeLifetimeTest`) — таблица выше соответствует реальному проекту.*
